DIFF FINDINGS
F1 [Low] Unbounded wait when the profile declares no timeout. If a profile has
   no timeout and no external cancellation arrives, a waiter polls forever
   (host_slot.go:121-167, 100ms interval) behind a stuck-but-alive holder.
   Holder identity IS revealed (announce at :110-120) so it is not silent, and
   decisions/621 Consequences documents profile timeout / external cancel as
   the only bounds. Advisory by design; accepted, recorded for awareness.
F2 [Low] Non-unix platforms hard-fail marked steps. os_other.go tryLock returns
   "locking is unsupported", so acquireHostSlot errors and the step fails
   (host_slot.go:150-151). Visible fail-fast, not a silent no-op; but config
   schema does not gate host_slot by platform, so a portable dva.yml with
   host_slot breaks on unsupported OSes. darwin/linux/BSD are covered by build
   tags; acceptable for this product.
F3 [Info] Lock-path symlink following. acquireHostSlot opens
   O_CREATE|O_RDWR without O_NOFOLLOW (host_slot.go:99); a pre-placed symlink
   under the UID-owned state dir could redirect the flock target or a rename
   could split waiters across inodes. The mechanism is explicitly cooperative
   and advisory within the user's own state root; not a security boundary.
   No action required.
F4 [Info] Torn metadata read. Waiters read the holder record without holding
   the flock (readHostSlotMetadata, host_slot.go:68-84) and can observe a
   truncate/rewrite in progress, briefly reporting holder=<unrecorded>.
   Transient and cosmetic; the flock remains the authority.
F5 [Info] Three-window budget widening is real but documented. runStep resets
   to the pre-budget origin after acquisition (cirun_steps.go:358), so a
   conditioned/reuse slot step can consume probe + execution + verification
   windows each of the full step timeout plus the wait, where a non-slot step
   gets one window. Documented in decisions/621 (예산 창 규칙, Consequences)
   and skills/dva-ci/references/configuration.md (corrected by f9310eff).
   No timeout value itself is raised; matches the card's stated rule.
F6 [Info] Release happens before the reuse verification window
   (defer release() in runStep unblocks when runStep returns;
   ci_reuse_step.go:83-95 verifies outside the slot). Another heavy step may
   start during verification. Verification is cheap input hashing; part of the
   documented three-window model.
Positive findings: failure/panic paths release correctly (deferred unlock,
   runStep defer release at cirun_steps.go:356; metadata-write failure unlocks
   before returning, host_slot.go:136-138); kernel reclaims flock on process
   death so crashes cannot deadlock, and the next holder overwrites stale
   metadata (documented); ancestor re-declaration fails fast instead of
   deadlocking (host_slot.go:154-160, tested); unmarked steps never open the
   lock file — gate at cirun_steps.go:314 plus bridge branch at :137 both key
   on step.HostSlot; config rejection exists in all three layers
   (ci.go:203-205 validation, schema.json host_slot boolean,
   ci_oci_serialization.go MarshalJSON/MarshalYAML) with tests incl. the
   YAML-1.1 "yes" schema gate.
