# CI 이벤트 계약 채택 계획

## 범위와 정본

2026-11-15 사용자 요청에 따라 [이벤트별 계약](ci-lifecycle.md)을 문서화한다.
현재 실행 기능은 [CI 프로필](53-ci-profiles.md), 재사용은
[결과 재사용](75-ci-result-reuse.md)이 소유한다. 이 계획은 새 hook·스케줄러·배포기를
도입하거나 소비자 저장소의 게이트를 변경하지 않는다.

이번 전달 단위 TASK-608은 계약·현황·채택 순서·에이전트 진입점의 완성이다.
검증 중 확인한 기존 테스트 lint 두 건은 사용자 허용에 따라 최소 수정한다.
테스트의 SplitSeq 반복 전환과 !windows 파일의 도달 불가능한 분기 제거이며,
제품 실행 코드·CI 설정·게이트 범위는 변경하지 않는다.
아래 후속 단계는 구현 완료로 계산하지 않는다. 실행 카드는 열린 일만 담고,
지속 참조할 계약과 인수 기준은 이 문서에 보존한다.

## 실행 순서

| 순서 | 작업과 소유자 | 선행조건 | 완료 기준 | 상태 |
|---|---|---|---|---|
| A | DVA: 이벤트별 책임·입력·범위·시간 목표 정본 작성 | 기존 계약 조사 | 모든 이벤트에 검사 목적과 차단 대상, 적용 상태의 작성 규칙이 있음 | 이번 전달 |
| B | DVA: 현재 선언과 미지원 기능 대조 | A | 아래 현황과 한계가 실제 파일에 대응하고 기존 게이트가 유지됨 | 이번 전달 |
| C | DVA: 문서·스킬 진입점 연결, 독립 검토·검증 | A, B | 링크·생성물·저장소 필수 검사와 독립 리뷰 통과 후 통합 | 이번 전달 |
| D | 채택 프로젝트: commit 경량화 파일럿 | A~C, 검사별 warm/cold 관찰 | 기존 필수 검사의 새 실행 경계를 명시하고 빠른 검사·통합 검사 양쪽 검증 | 후속 적용 |
| E | 각 CI 소유자: push/PR 중복 조정과 병합 결과 검증 | D, CI 권한·보호 규칙 확인 | 같은 변경의 중복 실행 정책과 최신 source/target 결합 증거가 확인됨 | 후속 적용 |
| F | 각 프로젝트: 일간·주간·산출물 검사 연결 | 별도 검사의 필요성과 자원 선언 | 자동·수동·해당 없음과 이유, finite timeout, 알림·실패 대응 담당자가 있음 | 후속 적용 |

작업을 재개할 때 이 순서와 아래 현재 상태를 먼저 대조한다. 코드·설정·검사 명령이
바뀌면 해당 단계의 증거를 다시 평가하며 완료 표시를 관성적으로 승계하지 않는다.
범위를 늘릴 때는 소유 저장소의 별도 실행 카드로 구체화한다. 미구현 항목을
문서가 있다는 이유로 자동화 완료라고 보고하지 않는다.

## DVA 자체 저장소의 적용 현황

관찰 기준은 TASK-608의 기준 revision `a19ee6569d172dd2fba41236368965ba36dc0e17`이다.
아래는 선언을 읽은 결과이며 원격 CI 실행 성공이나 branch protection 설정의 증거가 아니다.

| 이벤트 | 현재 연결과 검사 대상 | 상태·차단 범위 |
|---|---|---|
| 편집 중 | [dva.yml](../dva.yml)의 `dev`; `DVA_BASE`로 영향 패키지 선택 | 수동, 해당 실행 실패 |
| commit 전 | `commit`/`make ci`는 전체 core 검사이며 staged 전용이 아님 | 수동; 빠른 commit 목표는 미적용 |
| commit 메시지 | [.githooks/commit-msg](../.githooks/commit-msg) | hook 설정 시 자동, 잘못된 subject의 commit 차단 |
| 로컬 push 전 | 저장소 전용 pre-push hook 없음 | 미구현; host T2 규칙은 별도 적용 |
| 원격 branch push | [.github/workflows/ci.yml](../.github/workflows/ci.yml), `master`·`dev/**` | 자동, 원격 검사 결과 생성 |
| pull/fetch 후 | 전용 hook·전체 CI 없음 | 자동 전체 CI 해당 없음; 준비 변경은 수동 확인 |
| PR 갱신 | 같은 workflow의 `pull_request`, 대상 `master` | 자동; required-check 차단 설정은 미확인 |
| 병합 직전 | [.gz-git/readiness/check](../.gz-git/readiness/check)는 `ce task gate` 위임 | CE 경로에서 자동 보드 판정; 최신 병합 결과 CI 연결은 미구현 |
| 병합 후 | `master` push workflow | 자동, 병합 후 검사 결과; 선행 통합 검증을 대체하지 않음 |
| 일간 | CI workflow에 `schedule` 없음 | 미구현, 확대할 검사 범위부터 선정 |
| 주간 | CI workflow에 `schedule` 없음 | 미구현, 일간과 다른 보장부터 선정 |
| 배포 전 | [수동 공개 릴리스](52-manual-release-runbook.md)의 산출물 검사 | 수동 릴리스 절차; 애플리케이션 배포는 제품 범위 밖 |
| 배포 후 | 같은 런북의 공개 자산 postflight | 수동 릴리스 확인; 운영 서비스 health 검사는 제품 범위 밖 |

원격 workflow는 native Make/tool 경로로 DVA 자체의 복구 독립성을 검사한다.
이벤트 문서화를 이유로 DVA 프로필 호출로 일괄 치환하지 않는다.
현재 push·PR에서 플랫폼 matrix·통합 검사도 수행하므로, 새 기본 검사 묶음보다 넓다.
이를 줄이는 결정은 필수 검사·보호 규칙·중복 방지 정책과 함께 E에서 검증한다.

## 파일럿과 지원 차이

- 새 commit 목표는 [이벤트 계약](ci-lifecycle.md)의 채택 기준이다. 기존 런타임의
  commit 상한과 프로젝트의 기존 timeout은 그대로다. DVA 자체 `commit`을 2분으로
  줄이거나 race·전체 lint를 다른 경계로 옮기는 변경은 이번 전달에 포함하지 않는다.
- staged 전용 snapshot·일반 영향 분석은 DVA 공통 기능으로 보장하지 않는다.
  DVA 자체의 `tools/affectedtests`는 저장소 소유 도구다. 부분 staging을 지원하려면
  staged와 작업 트리의 차이·삭제·미추적 입력을 대조한 별도 검증이 필요하다.
- 실행 없는 유효 증거 조회와 checkout 간 재사용은 기존 TASK-607의 범위다.
  그 완료 전에는 pre-push를 증거 조회로 자동 생략한다고 선언하지 않는다.
  프로필 이름 `verify`와 향후 조회 CLI 이름은 구현 시 충돌을 확인한다.
- `audit`은 full과 동일 범위의 fresh 실행이다. 일간·주간 확대 범위가 필요하면
  다른 선택 프로필을 선언한다. fresh는 테스트 결과 캐시 우회이며 cold 빌드와 다르다.

## 검증과 인계

문서 인수는 이벤트 전수 대조, 현재 설정 대조, 독립 리뷰와 `make doc-check`로 한다.
스킬 변경은 `make generate`와 `make check-generate`로 투영을 확인하고,
통합 전 저장소가 요구하는 lint·full 검사를 수행한다. 문구 존재 검사만으로 설계
정합성 검토를 대체하지 않는다. 실패·미실행·제외 범위는 성공과 분리해 기록한다.

인계에는 TASK-608의 브랜치·revision, 변경 경로, 실행한 검사와 결과, 독립 리뷰,
통합·push·회수 상태를 남긴다. 후속 적용 D~F의 인수 기준과 미지원 기능은 이 문서에서
이어받는다. 다른 저장소의 채택과 설치본 갱신을 이번 문서 통합의 증거로 주장하지 않는다.
